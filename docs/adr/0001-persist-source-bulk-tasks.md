# 持久化来源批量任务并由后台统一编排

## Status

Accepted

## Context

Sources 页面原先只有单来源扫描与下载接口。对 100 个来源执行相同动作时，客户端逐个请求既无法在关闭页面后继续，也没有父任务进度、部分失败重试和统一取消语义。若客户端同时提交“刷新”和“下载”，下载 run 只能包含提交当时已发现的 Tweet，无法准确表达“刷新完成后只下载本轮新增”。周期执行还需要复用同一套背压、审计和恢复机制。

## Decision

- 在 Postgres 中持久化 `source_bulk_tasks` 父任务与 `source_bulk_task_items` 逐来源任务项，创建时冻结最多 200 个来源的成员快照。
- 支持“更新最新推文”“下载当前缺失项”“更新并下载本轮新增”三种任务；组合动作由服务端编排扫描与下载依赖。
- 扫描运行记录批量任务项，发现记录保存首次发现它的扫描运行，从而精确圈定本轮新增，不按时间窗口推测。
- 任务按 10 个来源一波推进，支持暂停、恢复、取消和仅重试失败来源。
- 扫描与下载共享单个网络 worker；两类工作同时就绪时交替执行，下载 run 按最近派发时间轮转。
- 定时策略只触发“更新最新推文”或“更新并下载本轮新增”，默认关闭；重叠或停机错过的执行合并成一次。

## Consequences

- WebUI 只创建和控制任务，不再为批量操作 fan-out 单来源请求；页面关闭与进程重启不影响任务审计。
- 精确的“本轮新增”需要新增数据库关联和迁移，但不会误把历史积压纳入组合任务。
- 波次与公平轮转限制队列灌入速度，代价是大型任务的总完成时间可能更长；计划时间表示 not-before，不保证准点完成。
- 手工下载超过 500 条需要确认；定时下载限制为每来源 50、每任务 1000，连续 3 个认证/限流错误会阻断父任务等待人工处理。
